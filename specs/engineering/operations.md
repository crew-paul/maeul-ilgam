# 운영·보안·배포 기준

## 계정·데이터 보호

이메일 인증 토큰은 짧은 유효기간·일회성·해시 저장·재전송 제한을 둔다. 세션 회전과 만료, CSRF 방어, HTTPS 보안 쿠키, origin 검사, 최소 CORS 정책을 적용한다. 운영자 계정에는 다중 인증과 최소 권한을 요구한다. 정지된 계정은 새 변경을 할 수 없다.

환경 변수와 배포 비밀 저장소로 키를 관리한다. 프런트 번들·오류 응답·로그·저장소에서 키가 발견되면 출시 차단이다. 기존에 노출된 API 키는 폐기·교체하고 운영 키로 재사용하지 않는다.

공개 프로필과 일감에는 필요한 지역만 표시한다. 개인 전화·계좌·상세 주소·검증 증빙·지급 증빙을 공개하지 않는다. 업로드는 형식·시그니처·크기·권한·다운로드 응답을 검사하고 악성 콘텐츠를 격리한다. 운영자의 비공개 열람은 사유와 감사를 남긴다.

## 보관·삭제

출시 전 운영 주체가 데이터 종류별 수집 목적·보관 기간·삭제/백업 만료 정책을 확정해 공개한다. 정책 승인을 받기 전 실사용자 모집을 시작하지 않는다. 구현은 계정 삭제 요청, 공개 정보 비공개화, 개인정보 삭제 작업과 법적/분쟁 보존 대상 분리를 지원한다. 음성 원본은 전사 완료·실패 후 짧은 TTL로 삭제하는 것을 기본으로 한다. 구체적인 TTL은 운영 설정과 정책에서 일치시킨다.

## 신고·운영

운영자 콘솔은 미확인 농가, 게시 검토, 불법/위험/허위 일감, 괴롭힘, 연락 두절, 지급 이견을 큐로 처리한다. 사유·담당자·처리 시각·사용자 통지·재검토 기록을 남긴다. 위험 일감은 즉시 공개/신규 신청을 중단할 수 있다. 운영자 처리로 당사자 확인이나 송금 사실을 대리 생성하지 않는다.

최초 제한 공개 전 실제 운영자, 지원 이메일, 대응 시간과 긴급 시 안내 경로를 지정한다. 농가 확인과 신고 대응을 맡을 사람이 없으면 실서비스 공개를 차단한다.

## 배포

환경은 개발·스테이징·운영으로 분리한다. 스테이징은 가상 데이터와 별도 키를 사용한다. DB 마이그레이션은 배포와 함께 버전 관리하고 되돌릴 수 없는 변경은 별도 검토한다. 프런트 빌드와 API는 동일 출처 HTTPS로 제공하고 워커는 내부에서 실행한다. 헬스체크·준비 상태·배포 버전·롤백 절차를 제공한다.

백업: 매일 자동 백업과 복구 가능 시점을 설정한다. 초기 목표 RPO 24시간·RTO 4시간. 이는 출시 검증 전 목표이며 실제 복구 연습으로 확인해야 한다. 복구 절차·담당자를 문서화한다.

## 관측과 목표

- 서버 오류율·응답 지연·DB 연결·outbox 지연·전송 실패·AI 429/비용·신고 적체를 모니터링한다.
- 개인정보 없이 request ID, 자원 ID, 오류 코드와 도메인 상태 변경을 추적한다.
- 초기 목표: 일반 읽기 API p95 1초 이내, 비-AI 변경 p95 2초 이내. 측정 환경·동시 사용자 수와 함께 결과를 기록한다.
- Meta 장애 때 수동 작성·탐색·신청·대화는 계속 동작해야 한다. 오류가 길면 기능을 일시 중단하고 운영자에게 알린다.

## 성과

게시 완료율, 문의/신청 도달률, 농가 응답 시간, 양측 수락 수, 양측 완료 확인, 지급 이견을 집계한다. 실제와 데모 데이터는 섞지 않는다. 측정에 필요한 동의·보관 정책을 따른다. 소수 이용자를 식별할 수 있는 공개 통계는 만들지 않는다.
